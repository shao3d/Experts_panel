# Аудит VideoHub и Скаута и сравнение моделей

Status: Evidence snapshot before implementation
Last updated: 2026-09-30

Проверены наполнение VideoHub, Матрица знаний, поиск Скаута и ответы трёх
моделей. Основной вывод: устройство системы разумное, но несколько переходов
между этапами не проверяют полноту данных. Из-за этого потерянный фрагмент,
незавершённое чтение и отсутствие материала могут выглядеть одинаково.
Смена модели улучшает ответы, но эти ошибки нужно исправлять в коде.

На семи одинаковых вопросах `gpt-6.1-sol` с reasoning `low` оказался наиболее
точным и полным. `gpt-6-luna` с `max` осторожнее Space Bunny, но тоже ошибается
в оценке полноты видео. Это вывод по данной небольшой выборке, а не оценка
моделей на всех возможных задачах. Рабочая модель на момент аудита не менялась.

Текущее поведение описано в [руководстве Скаута](../guides/expert-scout.md),
[архитектуре VideoHub](../architecture/video-hub-service.md),
[операторском руководстве](../guides/video-hub-operator.md) и
[доктрине admission](../architecture/expert-admission-control.md#16-videohub-sidecar-admission).
Результаты последующего внедрения: [правки и проверки](2026-09-30-videohub-scout-fixes.md).
Этот документ содержит результаты проверки и предложения, а не новую спецификацию.

## Границы проверки

- Исследованы код, профильная документация и сценарии отказов на синтетических
  данных. Реальный dev-корпус читался только через разрешённый инструмент Scout.
- Production, содержимое секретов, базы напрямую и сохранённые логи прогонов
  не читались. Живые события сравнительных запусков разбирались в памяти.
- Исходные видео заново целиком не просматривались и не транскрибировались.
  Нельзя утверждать, что каждый исторический импорт полон или повреждён.
- Воспроизведение опасного пути импорта доказывает дефект защиты, но не доказывает,
  что он уже испортил данные владельца.
- Изменения текущего ingestion, retrieval, Матрицы и проверок ответа не внесены.
  Добавлены только отдельный сравнительный стенд, MCP-адаптер существующего
  инструмента и тесты стенда.

## Что уже устроено хорошо

Разделение подготовки медиа, смысловой сегментации и импорта позволяет
перепроверять промежуточный результат. Транскрипт дополняется экранным текстом
и плотными кадрами в местах изменений. Это полезно для инструкций, где нужные
настройки видны на экране, но не произносятся.

Единый `expert_id=video_hub` разумен для отдельного канала знаний при условии,
что внутри него сохраняются автор и идентичность каждого ролика. Канонизация
YouTube URL, стабильные ключи, контроль повторяющихся segment_id и
транзакционный `--replace-video` уже решают часть проблем повторной загрузки.

У Скаута хорошая граница доступа: read-only SQLite, `query_only`, инструмент
без shell, передача аргументов массивом, изоляция выборок по эксперту.
Есть гибридный поиск, режим для старого полезного крафта, раскрытие источников,
диагностика поисковых веток и стенды. Переписывать систему целиком не требуется.

Матрица использует общую предметную классификацию и помогает выбирать новые
видео по потребности. Ей нужен надёжный учёт фактов загрузки и покрытия,
а не отдельная сложная графовая платформа.

## Очерёдность ремонта

Приоритет учитывает ущерб, частоту проявления и возможность небольшого
исправления. Редкая перезапись чужой записи опаснее косметического недостатка
ответа. Первая тройка — защита загрузки, полное чтение, честный статус ответа.

| Очередь | Исправление | Зачем |
| --- | --- | --- |
| 1, критично | Закрыть потери и пересечения при импорте | Не потерять знания до того, как их начнёт искать модель |
| 2, критично для точности | Исправить чтение страниц и принадлежность фрагментов видео | Не пропускать инструкции и не смешивать разные ролики |
| 3, критично для доверия | Различать успешный ответ, частичный результат и ошибку | Не выдавать сбой или непроверенное утверждение за найденный ответ |
| 4, высокий | Считать покрытие Матрицы по подтверждённым материалам | Не объявлять тему закрытой по одному решению загрузить видео |
| 5, высокий | Завершать индексацию с проверкой результата | Загруженный текст должен действительно участвовать в поиске |
| 6, высокий | Исправить ранжирование векторной ветки | Не терять хорошие кандидаты при поиске по нескольким экспертам |
| 7, средний | Согласовать стратегию агента, лимиты и контракт инструмента | Поведение должно переноситься между моделями |
| 8, средний | Дополнить приёмочные стенды проверками смысла и полноты | Не принимать улучшение только по числу найденных ключей |
| 9, после основного | Убрать ручные несогласованности и служебные дефекты | Снизить вероятность ошибок оператора |

### 1 Защитить сборку и импорт

**Подтверждено.** В `import_video_json.py` существующая запись ищется по
`telegram_message_id` без `expert_id`. На синтетической базе совпавший ID
позволил обновить запись другого эксперта как сегмент VideoHub. Виртуальный ID
ограничен миллиардом значений; даже добавления expert_id недостаточно для
защиты от столкновения двух видео. Нужна проверка исходной идентичности:
канонический video_id и исходный segment_id.

В `ingest_video.py::combine_chunks` одинаковая тема и близкий таймкод считаются
достаточным доказательством дубля. Два разных совета одной темы на 10-й и 30-й
секундах одного чанка превратились в один сегмент. Содержимое и происхождение
фрагментов не сравниваются. Рекомендация оператора менять topic_id ради обхода
этого правила ухудшает смысловую классификацию.

Сборка принимает только найденные файлы. При ожидаемых двух чанках отсутствие
второго не блокирует результат. Несогласованные URL в двух чанках тоже
принимаются; общие метаданные остаются от первого.

**Небольшой ремонт.** Проверять полный список ожидаемых чанков и совпадение
метаданных; разрешать неполную загрузку только как явно обозначенный scope.
Не удалять содержательно разные сегменты по одной теме и времени. Дедупликацию
ограничить подтверждёнными повторами из пересекающихся соседних чанков.
Перед обновлением записи проверять и эксперт, и исходную идентичность.

**Приёмка.** Чужая запись не меняется при совпадении ID; два разных совета
сохраняются; точный повтор на стыке не размножается; пропущенный чанк и чужой
URL блокируют импорт; повторная загрузка того же видео остаётся идемпотентной.

### 2 Дать Скауту полное чтение и понятные границы видео

**Подтверждено.** `expert_scout.py::cmd_digest` вычисляет смещение как
`page * window`, но ограничение по символам может вернуть меньше window.
Следующая страница перескакивает через невыданные строки. На 60 синтетических
записях окно 30 вернуло 28 + 28 + 0, затем `has_more=false`: четыре записи
потерялись. Окно 20 в этом примере отдало все 60, но это обход, а не исправление.

Digest отдаёт первые 400 символов записи. Это часто заголовок и summary,
а инструкция находится дальше. Даже исправленный обход digest не означает,
что агент прочитал весь текст. У большого `show` нет полноценного продолжения
при переполнении вывода; инструментальная среда тоже может обрезать ответ.

`show --expand` выбирает соседей по эксперту, дате и post_id. Все видео имеют
общего эксперта, поэтому сосед может оказаться из другого ролика. Проверка
на перемешанных сегментах двух видео воспроизвела именно это.

Важные метаданные не доходят до агента одинаково: JSON `show` содержит автора,
текстовый `show` его опускает; поиск и digest не дают полноценного каталога
роликов. Нет точного фильтра по video_id/автору. Поиск буквального YouTube ID
ненадёжен, поскольку ID не является обычным индексированным текстом.

`timestamp_seconds` используется как момент ключевого кадра, а не как
гарантированное начало смыслового отрезка. Длительность, исходные интервалы
и полнота ingest не передаются как строгий контракт. В живых прогонах обе
модели объявили разницу 14:15–18:06 пропуском материала. Одних таймкодов для
такого вывода недостаточно.

**Небольшой ремонт.** Возвращать курсор по реально выданным строкам,
`truncated` и следующий курсор. Разделить просмотр карточки и полное чтение.
Добавить идентичный паспорт видео во все форматы: video_id, автор,
published_at, тип таймкода, scope загрузки, известные интервалы. Неизвестные
границы так и обозначать; не вычислять их по соседним ключевым кадрам.
Дать фильтр по ролику; соседей выбирать только в нём и по времени.

**Приёмка.** Обход любой длины отдаёт каждый ключ ровно один раз; длинная
инструкция доступна до конца; соседи не пересекают видео; plain и JSON
дают одинаковую идентичность; агент различает «прочитал часть» и «в базе нет».

### 3 Исправить статус ответа и проверку доказательств

**Подтверждено.** Обёртка `expert_scout.sh` печатает любой непустой ответ и
может завершиться кодом 0 после таймаута движка либо провала проверки
целостности. Три сценария с подставным движком воспроизведены. Фильтр может
принять последнюю текстовую реплику за ответ без подтверждения завершения.

`verify_citations.py::fetch_sources` теряет запрошенные ключи при ошибке
подпроцесса или некорректном JSON. Проверка отсутствующих источников затем
смотрит только на полученные элементы. Воспроизведён результат exit 0 и
пустой список missing при неудавшейся проверке единственного ключа.
Ответ с фактическими утверждениями вообще без ключей также не блокируется.

Дословная цитата ищется сразу по совокупности источников и комментариев,
без привязки к указанному рядом ключу. Фрагменты с многоточиями могут
совпасть в разных местах. Наличие существующего ключа не доказывает,
что источник подтверждает соседнее утверждение. Синтезированный SUMMARY,
речь эксперта, экранная надпись и комментарий нельзя считать одним типом
первичного свидетельства.

**Небольшой ремонт.** Явные статусы `completed`, `partial`, `error`;
ошибка инструмента не является пустой выдачей. Проверять весь набор
запрошенных ключей, а не только успешно вернувшиеся. Вести в коде список
успешно раскрытых источников. Для цитат хранить пару «ключ + точный фрагмент»
и тип свидетельства. Пересказ проверять отдельной рубрикой; механическая
проверка строк не умеет доказывать весь смысл ответа.

**Приёмка.** Таймаут, сломанный JSON, несуществующий ключ и цитата из другого
источника не получают статус полного успеха. Честный ограниченный ответ
допускается с понятным описанием непроверенной части.

### 4 Сделать Матрицу учётом подтверждённых знаний

**Подтверждено.** `build_video_matrix.py::video_record` выставляет `in_corpus`
по verdict `ingest`/`ingest_scoped`, без проверки факта успешного импорта.
`ingested_at` переносится в запись, но не служит доказательством этого статуса.
Отсутствующие файлы сегментов не мешают учитывать заявленные cells.

Синтетическое видео, одобренное для 12 поддоменов, без единого файла сегментов
дало «загружено 1», ноль сегментов и ноль пробелов. Повторная запись одного
видео в журнале удвоила учёт. Topic IDs собираются, но доказательной связи
«ячейка → тема → конкретные source_key» нет. Пробелы считаются по наличию
поддомена, а не по конкретным вопросам, глубине или актуальности.

Показатель decay сейчас классифицирует version_lock/durable_share;
это не фактическое старение знаний со временем. Отсутствующая Матрица
экспертов молча превращается в пустой словарь сравнения.

**Небольшой ремонт.** Развести «выбрано для загрузки», «загружено»,
«доступно в поиске». Формировать квитанцию импорта с video_id, scope,
числом сегментов и ключами; подтверждать готовность индексации. Cells
подкреплять несколькими реальными segment/source_key. Обновлять запись
по video_id, а не суммировать повторные решения. Пустой результат Скаута
считать кандидатом на пробел только после успешного полного протокола поиска.

**Приёмка.** Одобрение без импорта не закрывает ячейку; повторный журнал
не удваивает покрытие; scoped-video закрывает только подтверждённые темы;
ошибка поиска не создаёт доказанный пробел.

### 5 Завершать индексацию и обновление метаданных

**Подтверждено.** По умолчанию `embed_posts.py` обрабатывает одну пачку 50
записей. Операторская команда без `--continuous` не гарантирует обработку
всех новых сегментов при большем объёме или накопившейся очереди.
Основная функция может завершиться успешно после ошибок пачки.

В режиме continuous постоянная ошибка не продвигает очередь и ведёт к
бесконечным повторам. Continuous с dry-run также читает ту же пачку снова;
аналогичный риск есть у force без курсора. Эти циклы воспроизведены
подставными результатами функции обработки, без сетевых вызовов.

При изменении только даты импорт обновляет post, но может оставить прежнюю
дату в vec_posts: синтетическая запись получила сентябрьскую дату,
а вектор сохранил январскую. При недоступном расширении vec инвалидирование
индекса может быть пропущено.

**Небольшой ремонт.** Ограниченная очередь конкретного импорта, проверка
числа ожидаемых/готовых векторов, ненулевой код при незавершённой работе,
ограниченные повторы ошибок. Согласованно обновлять поисковые метаданные.
Отчёт отдельно показывает готовность текста/FTS и векторной ветки.

### 6 Исправить преобразование расстояния векторного поиска

**Подтверждено.** `_rank_vector` использует `max(0, 1 - distance)`.
Индекс sqlite-vec настроен на L2. Расстояния больше 1 превращаются в одинаковый
ноль. На нормированных синтетических векторах кандидаты с расстояниями 1.1
и 1.4 перестали различаться. При объединении экспертов 40 дальних кандидатов
первого эксперта вытеснили более близкого кандидата следующего.

Внутри одного эксперта исходная сортировка SQLite иногда сохраняет порядок,
поэтому это не означает, что вся векторная выдача всегда сломана.

**Небольшой ремонт.** Согласовать score с фактической метрикой, сохранить
монотонный порядок и отдельно проверить влияние свежести. Сравнить recall
и MRR на зафиксированном времени; не менять одновременно эмбеддинги, веса
и структуру индекса без отдельного замера.

### 7 Сделать правила агента независимыми от модели

**Подтверждено по коду и прогонам.** В промпте есть ограничения числа поисков
и раскрытий и ранняя остановка после неудачных запросов. Они могут быть
слишком жёсткими для приоритета точности. Сужение по свежести с расширением
только при пустой выдаче пропускает старый полезный материал, если свежая
выдача непустая, но слабая.

Правило расширить поиск перед отказом конфликтует с запретом выходить за
явно указанный экспертный scope. Полнота и список доказательств в основном
доверены памяти модели. Схема плагина разрешает limit не больше 30, тогда
как промпт/хелпер говорят о 40; вызов с 40 отклонён в тесте MCP.

**Небольшой ремонт.** Единая схема инструментов, неизменяемый scope сессии,
видимый список проверенных аспектов вопроса и успешных чтений. Остановка
по покрытию аспектов или понятной причине, с общим техническим таймаутом.
Модель выбирает запросы и формулирует ответ; код отвечает за границы,
состояние чтения и происхождение доказательств.

### 8 Исправить приёмку качества

`agent_probe.py` может принять наличие слов о пробеле за корректный отказ,
не проверяя успех запуска и содержание ответа. Ошибочные `show` могут
попасть в счётчик чтений. Сравнение с отсутствующими результатами не всегда
считает их регрессией. Эти случаи воспроизведены синтетически.

Исторический baseline от 2026-09-29: mean recall@10 около 0.20,
recall@40 около 0.39. Это однопроходный retrieval на заданных ключах,
не процент правильных финальных ответов. В 24 поисковых фикстурах есть
видеоключи, но нет отдельно заданного scope video_hub; пять агентных
фикстур не покрывают специфические ловушки видео.

Сохранить существующие стенды и добавить реальные вопросы из сравнения:
два автора, дословная речь против экрана, scoped-video, ложный параметр,
старый крафт, отрицательный контроль. Оценивать поддержку утверждений,
полноту полезных инструкций, корректность отказа и отсутствие смешения
авторов. Число ссылок и длина ответа сами по себе качеством не являются.

### 9 Убрать операторские несогласованности

- `copy_frames` выполняется до завершения dry-run, поэтому пробный импорт
  может копировать кадры. Файловые действия не откатываются с SQLite;
  существующие одноимённые кадры не всегда обновляются.
- Combine не приводит относительные пути кадров к единой базе; руководство
  оставляет ручное исправление. Генератор Матрицы ищет артефакты в фиксированной
  раскладке, тогда как оператор может выбрать иной `--out`.
- Отрицательный таймкод, пустой текст и отсутствующая дата недостаточно
  строго валидируются; дата импорта может подменить дату публикации с warning.
- Нужна единая небольшая квитанция завершения загрузки и ясные ошибки,
  а не ещё один параллельный журнал состояния.

## Сравнение моделей на одинаковых вопросах

Luna и Sol запускались настоящим `codex exec`, без shell, web и других
исследовательских инструментов, с одним MCP-инструментом `scout`.
`scripts/expert_scout_mcp.ts` использует ту же схему и тот же execute
существующего OpenCode-плагина. Space Bunny запускался штатной обёрткой.
Промпт Скаута и корпус общие; отличаются модель, движок и упаковка tool calls.
Поэтому измерено поведение реальных конфигураций, а не изолированное свойство
весов модели.

Точные настройки: `gpt-6-luna/max`, `gpt-6.1-sol/low`,
`opencode/space-bunny-free` со штатным variant max. Поддержка режимов сверена
с [описанием Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)
и [описанием Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol).
Для сравнительных запусков поднят технический таймаут до 900 секунд:
обычные 300 секунд могли бы преждевременно оборвать несколько ответов Luna.

| Вопрос | Space Bunny | Luna max | Sol low |
| --- | --- | --- | --- |
| Max Novak, старый Switchlight/Blender workflow | Много деталей, но выдуманная полнота корпуса и пропуски между таймкодами | Верная основа; первый ответ пропустил несколько полезных операций | Подробный порядок, ручная подготовка и финальная доводка, ограниченные выводы |
| Youri, управление камерой, две точные цитаты | Полезные цитаты и multi-shot; неверное число доступных сегментов и выдуманные интервалы пробелов | Верные цитаты, различает речь и экран, замечает расхождение версий на слайде и в речи | Верные цитаты и происхождение; не включил отдельный полезный multi-shot пример |
| Max Novak против Higgsfield, роль Blender | Перепутал подготовительный PNG/EXR-export с финалом; чрезмерное отрицание роли AI у Max | Разделил методы; первый ответ объявил неуточнённой операцию, которая описана в другом фрагменте | Верно разделил этапы, ручную работу и корректировки между генерациями |
| Scoped-video OiULPvTJ-0E и первые 10 минут | Выдуманный внутренний пробел и слишком уверенная полнота | Осторожен насчёт начала, но тоже выдумал пробел 14:15–18:06 | Не выводит границы из таймкодов; явно описывает прочитанные части и неизвестное |
| Ложные temporal_strength=0.37 и ACEScg | Не подтвердил, но добавил необоснованные утверждения о полноте и экспорте | Не подтвердил и не выдал это за доказательство обратного | То же, с правильным разделением Switchlight и подготовки в After Effects |
| Acidcrunch, камера в Aleph | Полезно, но часть ссылок не раскрыта в зафиксированном show, есть широкие утверждения об отсутствии | Находит рекомендации и замечает противоречие про первые/случайные 5 секунд | Различает рекомендацию, демонстрацию и противоречивые ограничения |
| Отрицательный контроль про NGS | Не сочинил протокол, но чрезмерно уверенно заявил отсутствие во всём корпусе | Ограничил вывод просмотренным материалом | Ограничил вывод проведённым поиском; смежные новости не выдал за протокол |

На первой серии из семи вопросов медиана времени: Bunny 108 секунд,
Luna 217 секунд, Sol 85 секунд. Это наблюдаемая длительность конкретных
запусков с переменной нагрузкой, не гарантированная производительность.
Скорость не использовалась как критерий выбора.

Два вопроса — старый крафт и сравнение авторов — повторены для Bunny и Luna.
Bunny повторил ошибки с полнотой и ролью AI. Luna во втором ответе дал больше
нужных деталей, включая финальную доводку у Max. Это показывает вариативность:
нельзя объявлять модель неспособной по одному пропуску. Но нельзя и считать
единичный хороший ответ гарантией следующего.

На всех семи первых запусках Sol упомянутые source_key были раскрыты в
успешных `show`. У Bunny есть отдельные ссылки без зафиксированного раскрытия.
Это нарушение дисциплины чтения, а не доказательство несуществования ключей.
Ранние два ответа Bunny в plain-формате не поддерживались первой версией
парсера стенда; их счётчики раскрытия исключены из такого сравнения.
Смысловые ошибки оценивались по ответам и самим материалам, не по этим счётчикам.

Sol дополнительно повторил сравнение авторов и scoped-video. Основные выводы
сохранились, выдуманного интервала пробела снова нет, все цитируемые ключи
раскрыты. Однако повтор сравнения опустил финальную доводку Max в After Effects,
а ответ про scoped-video всё ещё называет отметки «началами записей».
Это неточное описание keyframe timestamps. У Sol также остаются пропуски
деталей и зависимость от слабого контракта метаданных; безошибочность не заявляется.
Всего выполнено 27 завершённых живых запусков: по девять каждой конфигурации,
из них семь общих вопросов и два повтора. Наборы повторов различались.

Автоматический quote checker ищет буквальное совпадение, а не доказывает смысл.
Правильная цитата с многоточием может не пройти буквальную проверку;
поэтому число совпадений не превращено в итоговый рейтинг.

**Рекомендация:** использовать Sol low как основной кандидат на замену,
Space Bunny оставить доступным для сравнения. Luna max улучшает осторожность,
но на этой выборке не даёт основания предпочесть его Sol. Даже с Sol нужны
исправления чтения и доказательств: модель не должна сама угадывать полноту базы.

## Выполненные проверки и воспроизведение

Пройдено 85 существующих профильных тестов: Scout, проверка цитат,
VideoHub guards/timestamps, Матрица, embedding runner и форма поисковых
фикстур. Четыре интеграционных теста с прямым обращением к настоящему helper
не запускались в этой серии. Для синтетических проверок был запрещён доступ
к настоящей базе и отключено чтение dotenv.

Дополнительно выполнены 32 изолированные проверки: девять для ingestion и
Матрицы, восемь для Scout, одиннадцать для верификатора/обёртки/метрик,
четыре для embedding runner. Они воспроизводят текущее ошибочное поведение
и его границы; это не 32 исправленных дефекта.

Новый стенд имеет девять тестов: успешное и неуспешное раскрытие, plain show,
ошибка инструмента, незавершённый turn, технический таймаут, две конфигурации
моделей и общая MCP-схема. Все девять пройдены.

```bash
backend/.venv/bin/python -m pytest backend/tests/test_scout_model_benchmark.py -o addopts='' -q
backend/.venv/bin/python backend/scripts/benchmark_scout_models.py --engine bunny --case scoped_video
backend/.venv/bin/python backend/scripts/benchmark_scout_models.py --engine luna --case scoped_video
backend/.venv/bin/python backend/scripts/benchmark_scout_models.py --engine sol --case scoped_video
```

Все семь вопросов находятся в `QUESTIONS` нового стенда. Данные для
добавленных тестов синтетические; MCP-тест отклоняет невалидные аргументы
до обращения к корпусу.

Полный свежий `search_probe --check-baseline` и штатный пяти-вопросный
`agent_probe` в этой серии не выполнялись. Их исторические показатели
не выданы за новые. Перед принятием runtime-исправлений они обязательны
вместе с новыми видео-кейсами. Одной смены модели и текущего сравнительного
стенда недостаточно, чтобы объявить весь поиск исправным.

Для аудита не нужны `выкатывай` или `обнови базу`. Code release и data release
не выполнялись. Исправления ingestion, индексации и формата данных нужно
принимать поэтапно; необходимость повторного импорта существующих видео
определять по квитанциям и проверкам конкретных роликов.
